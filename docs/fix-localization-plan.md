## Phase 0 findings & course correction (2026-06-12)

Phase 0 shipped (0.1/0.2/0.3) and the data **redirected the diagnosis**. The headline hypothesis below — that rescans compound drift and the saved map *degrades into a multi-session blob* until gen 3 can't localize — is **disproven**. What actually happened:

- **The gen-3 "never localizes" failure was a save bug, not drift.** The save path re-ran `makeConfiguration()` with `initialWorldMap=nil` before `getCurrentWorldMap`, detaching the session from the map it had relocalized into — so a relocalized generation persisted only the ~hundred feature points it observed itself. The map **collapsed** (gen-1 saved 5549 features → gen-2 saved **159**) — the *opposite* of blob growth. gen-3 then had 159 features to relocalize against and couldn't lock.
- **Fixed** ([CaptureView+Recording.swift](../wisescan-ios/CaptureView+Recording.swift), commit `e976c11`): mutate the *live* config (`sceneReconstruction=[]`, no `resetTracking`) instead of re-running a nil-map config, preserving the merged map. **Verified on device:** gen-2 now saves **10357** features (5549 inherited + new), and **gen-3 localizes in 3.9 s** with a clean settle.
- **ε is small and not (yet) compounding.** Settle landed ~12 cm from origin; ICP correction was ≈8 cm at gen-2, ≈1.5 cm at gen-3 — it went *down*, not up. The map **accumulates by area** (deduped), not unboundedly — re-scanning the same space converges because ARKit refines existing features rather than duplicating them.
- **No 25°/3 ft false-lock observed.** Every lock so far has been clean. The Phase-2 ICP gate still matters in principle, but we have **zero** gross-residual data to set its threshold.

**Effect on the plan:**
- **Phase 1's stated justification (stop catastrophic compounding) is gone.** A canonical frame is still wanted for **Phase 4 (3D-stitch durability)** and the **4D same-frame-every-visit** goal, but it is no longer a localization-*failure* fix. Priority drops; it is now **gated on 0.4 below**.
- **0.4 (the real Phase-0 exit) is CLOSED (2026-06-15) with a TWO-PART result:**
  - **(a) For an *identical* re-approach, ε is bounded** — settle pose held to ~1.5 cm across gen 3/4/5, ICP correction decreased. No compounding off the relocalization chain. → **Phase 1 stays demoted** (it fixes *which* map you relocalize against, which was never the problem).
  - **(b) ε is APPROACH-DEPENDENT and decimeter-scale.** When the start standpoint differs (gen 6/7), the relocalization registration error jumps to **~25 cm** (gen-7, the trustworthy measurement: 99% inliers, well-constrained, `trans=25.4cm`; gen-6's `68cm` was the same effect *overstated* by 46% partial-overlap letting ICP wander). The careful "same start to the inch" protocol on gen 3/4/5 was *masking* this — few-cm reproducibility came from re-approaching identically, not from relocalization being intrinsically tight. **This is the real product problem:** 4D users won't re-approach to the inch, so meshes land ~25 cm apart across visits. **The fix is Phase 2.1 (ICP-refine the relocalized pose against the canonical mesh before save), NOT Phase 1.**
  - Residual watch (map longevity, NOT ε): `features` oscillates with coverage (10357→11585→15677→15218→19718) — went *down* at gen-6, so it tracks coverage rather than accumulating monotonically; not a runaway. Keep an eye across equal-coverage passes.
- Failure mode #2 (frozen-layer desync) is unchanged and **deferred by decision** — the saved/colorized preview renders from the saved mesh, not the live `world:.zero` layers, so it is correct today; live-viz fixes (Phase 3) wait.

Also shipped this pass (scanning robustness, not localization-plan items, but they keep relocalization runs clean): a **VIO-guard fix** (commit `03acb18` — a bare frame-delivery gap from a compute hiccup no longer halts the scan; it must be corroborated by hard-degraded tracking, and `.relocalizing` is treated as benign recovery) and a **double-save guard**. Relevant here only because a session cut mid-relocalization can't localize.

## Background — what's broken and why

**Symptoms (observed on device):**
- 1st scan of a space is fine. 2nd scan localizes but with a **consistent offset**. 3rd scan starts the AR session but **never localizes** (or lands ~25°/3 ft off). *(2026-06-12: the gen-3 "never localizes" turned out to be a save bug — now fixed; see "Phase 0 findings" up top. We have **not** reproduced the ~25°/3 ft false-lock; treat that parenthetical as unverified.)*
- Within a single render, layers **diverge from each other** — the live mesh sits on reality while voxels / connectors / ghost mesh drift off.

**Root cause (two failure modes, one false premise).**

Every visual layer was built on the assumption that an `ARWorldMap` re-establishes a **fixed, reproducible coordinate frame** each time you load it — so geometry baked to that frame's numbers will align in passthrough/VR. That premise is false in the part that matters:

- An `ARWorldMap`'s **internal** frame (feature/anchor coords relative to its own origin) *is* immutable across loads. ✅
- Its **registration to physical reality** is **re-estimated on every relocalization with fresh error each time**. The origin (`0,0,0`) is an arbitrary `t=0` datum with no physical pin; it rides that re-estimate. ❌
- The only thing fixed to reality is an **`ARAnchor`** — ARKit re-pins anchors to their physical feature every frame as the floating frame corrects. The coordinate frame floats *by design*; anchors are the remedy.

From that, two distinct problems:

1. **Compounding (the chain).** ⚠️ **(2026-06-12: this is the failure mode Phase 0 DISPROVED — see "Phase 0 findings" up top. The gen-3 failure was a save bug that *collapsed* the map to 159 features, not drift that bloated it into a blob; the map actually accumulates healthily and gen 3 localizes after the fix. The "relocalize against the latest scan" chaining is still architecturally worth changing for Phase 4 / frame stability, but it is NOT what caused catastrophic failure. Kept for history.)** Rescans relocalize against `sortedScans.first` — the **latest** scan ([LocationDetailView.swift:117](../wisescan-ios/LocationDetailView.swift#L117) / [:140](../wisescan-ios/LocationDetailView.swift#L140)) — and re-save a *new* merged world map. So each generation bakes a fresh relocalization error on top of the last, and the saved map degrades into a multi-session blob. By gen 3 the map is offset *and* an ambiguous relocalization target → catastrophic failure. (The [CaptureView.swift:133-138](../wisescan-ios/CaptureView.swift#L133-L138) comment treats this chain as a lossless "continuous frame" — it isn't.)

2. **Frozen-layer desync.** Nearly every overlay is placed with RealityKit `AnchorEntity(world:)` — a one-time static placement that does **not** follow ARKit's ongoing corrections (loop closure, post-relocalization snaps). The live wireframe even bakes `ARMeshAnchor` geometry into world coordinates under `world:.zero` ([ARCoverageView.swift:735](../wisescan-ios/ARCoverageView.swift#L735)). So after any frame correction, baked layers lag while the camera and live anchors move — hence the layer-vs-layer divergence.

**Reframe for our target hardware:** we target **LiDAR** devices. Sub-degree / few-cm relocalization noise is acceptable. **25°/3 ft is not drift — it's relocalization *failure*** (wrong-feature lock on a degraded map). The fix must therefore (a) **never compound**, and (b) **never trust a relocalization it hasn't geometrically verified** with the LiDAR mesh.

## Target architecture

- **One fixed canonical frame per location.** A designated canonical map defines the location's coordinate space permanently. All scans — 4D repeats included — relocalize **into** it and never redefine it. Re-baselining is a deliberate, versioned op, never a side effect of a normal scan.
- **LiDAR ICP as the trust layer — registered to *structure*, not content.** `ARWorldMap` relocalization is a *coarse bootstrap*; point-to-plane ICP of the live LiDAR mesh against the canonical mesh **refines** the pose and yields a **residual** that **gates** the save (rejects the 25°/3 ft locks). ARKit gives a tracking *state*, not an alignment *error* — the residual is the missing signal. Crucially the ICP registers against the **stable scaffold** (walls/floor/ceiling/built-ins), not all geometry, so moved furniture can't bias or fail the lock — see "Scene change vs. registration" below.
- **Pose graph over location frames (3D stitch).** Inter-location transforms are edges between *canonical frames*, not scan instances. 4D updates register into a frame and never move it, so they **can't disturb** the 3D layout. The graph changes only on deliberate re-baseline.
- **Overlays ride the live frame.** Every layer derives its pose the way the camera feed does — current-session geometry bound to live `ARMeshAnchor`s; cross-map geometry bound to `ARAnchor`s stored in the world map — never baked to frozen numbers.

### The two product modes this must serve
- **4D (scan in time):** one space, repeated scans over time, each colored mesh landing in ~the same coordinate frame each visit → served by the fixed canonical frame + ICP-refined registration.
- **3D (stitch space):** many known locations stitched together, transforms holding even as individual locations are updated in 4D → served by the pose graph over fixed canonical frames.

### Scene change vs. registration (the 4D contract)
4D *is* change capture — furniture moves, objects come and go, and over a long horizon **structure itself changes** (a wall comes down, a room is renovated). The system must register reliably *through* that change and treat the change as the **product**, never as registration error. The mesh-to-mesh difference between a good relocalization in a redecorated room and a blown relocalization looks identical to a naive global RMS — so the design must separate the two.

**One principle: separate the *frame* from the *content*. Register to what doesn't move; the part that moved is the 4D signal.** This yields three regimes, handled distinctly (not two):

1. **Content change (furniture rearranged) — normal 4D.** Register to the stable scaffold; moved objects have no canonical surface nearby, so they fall out of the ICP inlier set automatically and can't bias the pose. The **outlier fraction is the change metric** — reported, not rejected. Inlier residual stays small (few cm); inlier fraction stays high.
2. **Partial structural change (a wall moved, an extension added) — still registerable, and high-value 4D data.** Enough original scaffold usually survives to register into the canonical frame on the *surviving* structure. The changed structure shows up as outliers **classified as wall/floor/ceiling** (vs. seat/table) — that semantic split is what distinguishes "someone moved the couch" from "someone moved the wall," and the latter is a higher-priority change alert.
3. **Wholesale change (renovation; too little scaffold survives) — graceful re-baseline, not silent failure.** When the inlier fraction drops **below the trust floor**, you genuinely can't register into the old frame. Don't reject silently and don't save garbage: detect it from the data and **surface a versioned re-baseline** (Phase 4.4). **The original baseline is never moved** — it stays the permanent coordinate authority because connector/stitch transforms are pinned to it. Re-baseline pins a *new generation* to gen 0 via a measured old→new transform (the surviving connectors double as the fiducials that measure it), so the 3D graph and the timeline stay intact.

**Implications that propagate into the phases:**
- The save gate is **not** a global RMS. It is **(inlier RMS < threshold) AND (inlier fraction > floor)**, with outlier fraction (classified) logged as the change metric (Phase 2.2/2.3).
- "Stable scaffold" comes from semantics already in the app — RoomPlan surfaces and/or `.meshWithClassification` (wall/floor/ceiling vs. furniture). Restrict/up-weight ICP correspondences to structural classes; geometric fallback = the large planes. 
- The canonical scan is chosen for **structural completeness**, not recency or being-first — it's the registration reference forever. Canonical = frame + scaffold; the **latest** scan always defines current content (Phase 1.1 / Open decisions).
- Re-baseline is **data-triggerable** (inlier fraction below floor, or sustained structural-class change), versioned, and timeline-preserving — not only a manual renovation op (Phase 4.4).

#### Implementation notes (code landed)
All three probes live in [LocalizationDiag.swift](../wisescan-ios/LocalizationDiag.swift), **log-only** and gated behind the existing `perfDiagnostics` Developer-Mode flag (same channel as the VIO instrumentation — `PerfDiag.log`, OSLog subsystem `org.arenaxr.scan4d`/category `perf`). Nothing changes capture behaviour; safe to leave compiled in. Log lines are tagged for grepping: `[LocDiag ε]`, `[LocDiag ICP]`, `[LocDiag snap]`.

Hook sites:
- **0.1 map stats** — [ARCoverageView.swift `makeConfiguration`](../wisescan-ios/ARCoverageView.swift) logs feature-point count / anchor count / extent / center every time an `ARWorldMap` is deserialized (the single chokepoint for all load paths).
- **0.1 settle pose** — `driveAlignmentPhase` logs the live-camera pose (position + yaw/pitch/roll, relative to the map origin = `0,0,0` after reloc) the moment relocalization first reaches `.normal`, plus seconds-to-settle. One-shot per alignment; reset on record/nominal transitions.
- **0.2 ICP** — ghost OBJ is stashed in `loadGhostMesh`; live world-space verts are sampled (capped per anchor) in `buildWireframeForAnchor` and, once ≥4000 accumulate during a relocalized recording, run **once** through a compact point-to-plane ICP (voxel-grid NN, subsampled, ≤14 iters, 6×6 Gauss-Newton) off the delegate queue. Logs `initialRMS` (residual at the relocalized/identity pose — the gross-failure signal), `finalRMS` (achievable floor), and the recovered correction (trans cm / rot °).
- **0.3 snap** — `SnapTracker` in `session(_:didUpdate:)` logs any single-frame camera-pose jump > 2 cm / 0.5° (the frame correction a baked `world:.zero` overlay does **not** follow).
- **Per-run summary** — a single `[LocDiag SUMMARY]` line is emitted at stop-recording for every relocalized run, consolidating map features/anchors + settle pose + ICP result + snap max/count, all **computed on-device** (no off-device math, no transcription — copy one line into the table). Summary state is main-thread-only; the delegate/ICP-queue probes hop to main to populate it. (If ICP is still in flight at stop, the summary shows `ICP: pending` and the standalone `[LocDiag ICP]` line carries the numbers — rare, since ICP triggers early in the pass and runs in ~tens of ms.)

**Important architectural finding (shapes Phase 2.1).** `sceneReconstruction` is `[]` during the pre-record relocalization/alignment phase — live `ARMeshAnchor`s only exist *after recording starts* ([ARCoverageView.swift:271-273](../wisescan-ios/ARCoverageView.swift#L271-L273)). So the ICP residual (0.2) is measured **during recording**, not at the settle moment. Phase 2.1 wants to "apply the ICP correction before `isRecording` flips on" — that will require enabling mesh reconstruction *during* the alignment phase (or a brief mesh pre-roll) so there's a live cloud to ICP against before the gate. Flagging now so 2.1 budgets for it.

#### HOWTO — run the profiling by hand (device-only; ARKit doesn't run in the simulator)
1. **Enable the flag.** Build to a LiDAR device, open **Settings → Developer Mode → Performance Diagnostics** (the `perfDiagnostics` toggle). Without it, every probe is a no-op.
2. **Open a log stream** (the values are logged `privacy: .public`, so they show literally — not `<private>`). Either:
   - Xcode console with the device attached, **or**
   - `Console.app` → select the device → filter on subsystem `org.arenaxr.scan4d`, **or**
   - terminal: `log stream --device --predicate 'subsystem == "org.arenaxr.scan4d" && category == "perf"' --style compact | grep '\[LocDiag'`

   Each relocalized run ends with one paste-ready consolidated line — everything computed on-device:
   ```
   [LocDiag SUMMARY] map=scan_3.arworldmap features=12043 anchors=2 | settle: pos=(0.83,1.42,-0.19) yaw=-23.4° (3.2s) | ICP: initRMS=84.2mm finalRMS=11.0mm corr(trans=7.3cm rot=2.10°) inliers=1840/2500 (74%) iters=9 | corrections: count=4 maxΔpos=4.1cm maxΔrot=1.30°
   ```
   The individual `[LocDiag ε]` / `[LocDiag ICP]` / `[LocDiag snap]` lines are still emitted for detail/debugging, but the SUMMARY line is all you need to fill a table row. (For the **never-localizes** case there's no recording → no SUMMARY; grab the single `[LocDiag ε] map load …` line instead.)
3. **Mark a physical standpoint.** Put a piece of tape on the floor. Every generation below, start the scan standing *on that tape, facing the same wall* — this is what makes the `[LocDiag ε] settle` camera pose comparable across generations.

6. **Generation 3 (the unfixed failure).** **Rescan Space** again → stand on the tape. Now the target is the gen-2 *merged* map. Two outcomes, logged differently — record whichever you get:
   - **Never localizes** (session starts, tracking never reaches `.normal`): `[LocDiag ε] settle` **never fires**, recording never starts, so `[LocDiag ICP]` **never fires** either. The proof is that *absence* **plus** the `[LocDiag ε] map load … features=N` line showing N **inflated vs. gen 2** (the multi-session blob). Note "did not localize" in the table.

This is the reject end of the threshold.
7. **Retry the failure as many times as you want (manual reset).** Each rescan that *does* save bumps the relocalization target forward, so to re-test gen-3-against-gen-2: in the location detail, **delete the most-recent scan** to roll the target back to the gen-2 map, then rescan again. (Recreating gen 2 from scratch works too — same effect.) Repeat to see whether the failure is consistent and to get a few residual samples for the threshold.
8. **4D change trials (proves the gate must use *inlier* RMS, not global RMS).** From a known-good gen-2 baseline:
   - **Move furniture, then rescan.** Shift a couch/table/boxes, relocalize, record. Expect: ICP `initRMS` stays **small** (walls/floor still align) while the **inlier % drops** (the moved geometry no longer matches). This is the signature of *content change* — and it must **pass** the gate, with the missing inlier % being the 4D change signal.
   - **Move/remove structure, then rescan.** If feasible, change something structural (open/close a partition, move a large shelving wall). Expect inlier % to drop **further**; this is regime 2/3 territory. If inlier % falls below where you'd still trust the lock, that's your candidate **inlier-fraction floor** (→ Phase 2.3 / re-baseline trigger).

The discriminator to confirm: *small initRMS + reduced inliers = real change (accept); large initRMS or collapsed inliers = registration failure (reject).*

Each line is how far a frozen `world:.zero` layer fell behind reality at that instant. Easiest to provoke: walk a loop back to a previously-seen area mid-record.

#### ★ PRIMARY registration approach (pivoted 2026-07-09) — plane-based, save-time room-to-room registration
> **Pivot:** the dense mesh-ICP bake (Phase 2 / 2.1 — all the validated-on-device work above) is **demoted to background reference**: keep its findings and code as a fallback idea, but it is no longer the path. **Plane-based registration is now primary.**

**Why pivot.** Dense point-to-plane ICP is (a) **brittle to lumpy LiDAR mesh** — shallow, ambiguous minima on noisy geometry, so it wanders and can fabricate offsets; and (b) **scales terribly with room size** — NN over 10⁵–10⁶ surfels, and all the `localizedTarget`/cap machinery exists only to fight that. Plane-matching is cheap, **robust to lumps** (planes average the noise out), scales with **surface count not face count**, and is **apples-to-apples** with the RoomPlan surfaces we already persist. Cost context that forces the issue: even the **initial** scan (no ghost — just ARWorld + mesh reconstruction + RoomPlan) already strains CPU as rooms grow, and pre-scan hit ~400% core util *with the rest of the system idle*. So the rescan must add as little as possible on top — dense ICP + a full second mesh is the opposite of that.

**The core fit:** a **plane-to-plane** rigid registration of live **walls (vertical planes / horizontal normals)** against the ghost's walls. ~5–20 planes ≪ NN over thousands of surfels → the hot loop disappears. The observability rule + inter-axis weighting below govern the solve; the two big structural decisions are the **mechanism** (save-time vs live) and the **ghost rendering** — both new (2026-07-09), below.

**Observability rule (the core geometry — carries over exactly from `horizMin`):**
- Horizontal translation + yaw are observable iff you have **≥2 walls with linearly-independent normals.** Two *parallel* walls (a bare corridor) = one independent normal → the along-axis floats (unrecoverable by *any* geometric method).
- **It's the normal *direction* + area, not the wall count.** A 3rd parallel wall adds nothing; a wall 5° off-parallel barely helps; a wall at 90° helps fully. So gate on the **eigenvalue** (`horizMinObservability` = smaller eigenvalue of the 2×2 horizontal normal block), never a wall count — a count misfires (3 near-parallel walls read "enough" but aren't).
- **Cubicle row / two sets of parallel walls = recoverable**, because the dividers/cross-walls are the structurally-guaranteed "≥1 non-parallel wall." The offset seen there is a **conditioning** problem (weak axis out-voted by the high-area long walls), not an ambiguity → fixable by weighting.

**Inter-axis (whitening) weighting — the upgrade over 2.1a:** 2.1a is only wall-vs-floor weighting. Go further: **up-weight the under-represented horizontal normal direction** (the sparse cross-walls) so the abundant long side-walls don't dominate the solve and leave the weak axis sloppy. Principled form: whiten by the same 2×2 horizontal block already computed for `horizMin` → drive the block toward isotropic. Existence (≥2 independent normals) gets you *past the gate*; whitening gets you a *tight* fit on the weak axis instead of a merely-present one. **Cap the up-weight** (ceiling, mirroring 2.1a's floor) — leaning on a few divider faces trades long-axis slop for variance; there's a bias/variance knee to tune. Composes with the gate: weighting **expands** the recoverable regime; `horizMin` still **backstops** the truly-degenerate.

**Scope boundary (explicitly NOT engineered for):** periodic repeating structure on the weak axis (repeating pillars / identical cubicles) is beyond saving — it defeats **relocalization itself** (the 71/22 flip-flop, the 7 m hallway loop-closure jumps: ARKit lands in the wrong *period*), and no downstream registration refinement lives below a wrong-period relocalization. That's the physical-fiducial case, full stop.

**Degradation ladder (2026-07-20) — how strong is the wall constraint, and what falls back where.** The engine's true requirement is NOT "4 walls": it's **2 walls with independent normals + a floor** (one good corner) — the 4-wall rectangle is 2× redundant (that redundancy is what trim rescue spends). Below the corner the MATH already degrades gracefully (Tikhonov ⇒ an unobserved DOF resolves to ~0 correction, i.e. inherits relocalization); what's binary today is the GATE (`weakAxisFrac` refuses everything, even the observable DOFs). Design-only for now — nothing on this ladder is scheduled; pull rungs forward when a real space binds the constraint. The floor of the ladder is never "unaligned": it's the raw relocalized frame (ARKit's own ~5–15 cm alignment, visually decent on a good seat — validated 2026-07-20); every rung only *refines* that. All rungs emit the same artifact (rigid raw→canonical + `registration.json`), so fallback engines slot in behind a sidecar `method` field without touching gates/viewer/ghost/2.2-UX.
1. **≥3 matched walls + floor** — full fit + trim-rescue consensus vs one bistable wall. ✅ today (v2).
2. **A corner (2 independent walls) + floor** — fully observable, zero redundancy: a bistable wall is undetectable (consensus needs a 3rd opinion). Missing piece = an *independent estimate*, not more walls: **persist the prescan live auto-align fit** (11 mm RMS, discarded today) as a prior/cross-check — two independent estimates agreeing within cm is consensus that costs no wall. (Small build.)
3. **Parallel walls / one wall + floor (corridor)** — **partial-apply**: correct the observable DOFs (perpendicular offset, yaw — corners give it a lever arm — and height), leave the weak axis at relocalization. Per-eigenvector gating instead of all-or-nothing; the eig2x2 machinery already computes the needed decomposition. Never worse than refusing. (Small build.)
4. **No usable walls, distinct static structure** (machine in open space): (a) content planes — RoomPlan object faces / unclassified ARKit planes, down-weighted + consensus-gated (content is exactly what MOVES between visits — trust design needed); (b) **postprocess mesh ICP — DECISION 3 removed dense ICP's main disqualifier** (live CPU/VIO contention is gone at postprocess), and distinct structure is dense ICP's *well-conditioned* case (its wandering was on lumpy near-planar rooms). Engine exists + device-validated (`LocalizationDiag.refine`); needs mesh-vs-mesh-from-disk plumbing, same trust gates, init at relocalized pose. (Medium build.) ⚠️ Today's BAD-scan state fights this rung: no-roomplan ⇒ "redo scan", conflating "RoomPlan failed on a room" with "space isn't room-shaped" — must soften before rung 4 exists.
5. **Nothing distinct / repeating structure** — fiducials (physical tags, or opportunistic ARKit image anchors on existing signage/posters) or accept raw relocalization. Out of scope by standing decision (above).

**DECISION 1 — Registration mechanism: SAVE-TIME correct-at-export (primary); live bake (fallback).** Prefer computing the correction at **save**, not live:
- Record the rescan in the **raw relocalized frame** (no live `setWorldOrigin`).
- At save, register the **final `RoomBuilder` room** (this rescan, fully built) against the ghost's **persisted final room** (`roomplan_raw.json`) → a plane-to-plane rigid transform → apply it to the exported mesh + world map (or store it as the scan's transform-into-canonical).
- **Wins:** max-quality **apples-to-apples** (both sides complete RoomBuilder output, same fitter); **zero live/VIO-competing cost** (runs in the existing 15–25 s save pipeline where RoomBuilder already executes); **deletes the entire live-bake hot path** — no mesh-during-alignment, no pre-record refine, no green chip, no record-await, no timing races; and it **unifies Phase 2.1 with Phase 1.3** ("store each scan's transform into the canonical frame") into one save-time step.
- **Tradeoffs (accepted as worthwhile):** (i) **no live alignment feedback** — the ghost overlay stays offset by ε during the scan; only the saved result is corrected (fine for rescan-to-recapture; the real thing given up). (ii) **co-framing by hand** — the live bake co-framed mesh+map for free via one origin shift; save-time must apply the transform to both (or store T + apply on load) — this *is* the Phase-1.3/4 data-model work. (iii) **depends on RoomBuilder succeeding at save** → on timeout/failure, fall back to raw/uncorrected. (iv) loses the dense furniture-level content-change metric → structural (wall-level) change instead.

**DECISION 2 — Ghost RENDERING during rescan: decimate; RoomPlan for alignment only, NOT coverage.** The ghost overlay has two purposes that want different things:

- **(b) coverage / "painting" guide** (how far to scan to re-cover the original extent in the new time slice): needs the **honest captured extent** — and this is where **RoomPlan misleads**: it **closes spaces and extends walls**, so on a partial capture of a large space or a hallway it fabricates boundaries and would tell the user to paint area the original never covered. RoomPlan is **wrong for the coverage guide.**

Three files persist per scan: (1) **full mesh** (artifact, unchanged), (2) **RoomPlan** (`roomplan.json`/`_raw` — walls + registration target, already written), (3) **decimated wall-subtracted non-wall proxy** (new; rescan overlay only).

#### ★ FOLLOW-UP DIRECTION (2026-07-16) — registration-mode ladder for nonstandard rooms
> **Framing:** the journey so far — started with full mesh-to-mesh ICP (Phase 2, device-validated, then demoted), pivoted to plane-to-plane via RoomPlan + plane detection (the PRIMARY above). The plane path stays primary, but it implicitly assumes a **traditional 3–4-wall room**. Real deployments include rooms that break that assumption: a large room with maybe **one reliable wall** (a single focal area mid-wall), or **no walls at all** (scanning the center of a big space, hoping for mesh features). Rather than one method stretched across all of them, expose the ladder we already built as **selectable registration modes**.
>
> **The three room regimes → three modes** (semantics to be workshopped — needs a user-interpretable classification, maybe a slider; "traditional / less traditional / very unusual" is the placeholder):
> 1. **Traditional room (3–4 walls)** — the default/common case → the full current PRIMARY path: RoomPlan rooms both sides, save/postprocess-time plane-to-plane registration. Nothing changes.
> 2. **Less traditional room (~1 wall-ish)** — RoomPlan adds little here (it closes/extends what it can't see, and one wall barely constrains its room model) → **plane-detection-API end-to-end, no RoomPlan**. Register persisted `ARPlaneAnchor` sets against live ones. Groundwork already in: the live ghost auto-align *already* does exactly this live side (`PlaneRegistration.planes(fromPlaneAnchors:)`, classification-gated) — mode 2 is mostly (a) persisting the plane-anchor set as the scan's registration artifact (the `roomplan.json` analog) and (b) skipping RoomPlan entirely. The `PlaneRegistration` solver is source-agnostic (takes rectangles, doesn't care who made them), so it carries over unchanged — as do the observability gate + whitening (a 1-wall room will often sit at `weakAxisFrac≈0`; the gate honestly reports which DOF are constrained, and partial registration beats fabricated).
>    - **Concrete wins beyond registration:** dropping RoomPlan removes its continuous CoreML from the recording phase — measured as part of the heavy `unnamed` CPU load (2026-07-13 AR-mode confirmation) — and saves **~100 MB memory + real model CPU on live scan**. Plane anchors can still stand in for the proxy's wall/floor quads and aid the **mesh decimation/simplification** effort (the DECISION-2 wall-subtraction doesn't need RoomPlan specifically, just plane rectangles).
> 3. **Very unusual room (no walls)** — nothing for a plane fit to hold onto → **mesh-only ICP**, reviving the demoted Phase-2 engine (`LocalizationDiag.refine` — device-validated: sign correct, gates work, `horizMin` eigen-split, best-pick). Crucially, run it where the plane path already runs: **at postprocess, offline, where CPU is free** — the "save-time mesh polish" idea from the DECISION-1 validation note, promoted from polish to sole registrar for this mode. None of the live-bake hot-path baggage (mesh-during-alignment, green chip, record-await) comes back; the brittleness/scaling objections that demoted mesh-ICP were about the *live* path and about it being the *default* — as an opt-in offline mode for wall-less spaces it's the right tool.
>
> **Planes serve TWO decoupled goals — alignment AND mesh simplification — apply each as practical, independently (refined 2026-07-16).** The ladder above governs *registration* only. Simplification (quads standing in for wall/floor faces in the ghost proxy) pays off wherever *any* plane is detected: one wall that's insufficient to constrain alignment still deletes a big slab of polygons from live rendering. So plane detection stays on in every mode and the proxy builder consumes whatever planes exist; the mode decides only what the *registration* trusts. (This means even mode 3 can carry a partial-quad proxy if a stray plane shows up — the "no quads in mode 3" assumption below is the degenerate case, not the rule.)
>
> **Hybrid registration (the modes-2/3 middle ground) — a composite plane+mesh fit MUST weight by represented AREA, not sample count.** The current focus mode registers *solely* on planes. But a hybrid ghost — say 2 simplified walls + simplified floor + a handful of lumpy content meshes — implies a composite solve over both primitive types, and the raw counts there are pathological: each lumpy chair carries **orders of magnitude more faces/points than a quad's samples** (`PlaneRegistration` samples 5 per plane), so a count-uniform ICP would let the content out-vote the scaffold — exactly backwards. The planes are the clean, *stationary* scaffold; the content is the 4D change signal that **may have legitimately moved** since capture. Two-part fix:
> - **Unified currency = surface area.** `PlaneRegistration` already weights plane samples as `area/5` — extend that currency to the mesh side (each surfel/point weighted by the area it represents, ≈ its voxel-cell footprint). A 12 m² wall quad then outweighs a 0.5 m²-of-surface chair *regardless* of the chair's face count. This is a weighting-schema unification, not a new solver.
> - **Content terms additionally capped/robust.** Even area-fair, content deserves a lower trust ceiling (robust kernel or weight cap — the mirror of 2.1a's floor-de-weighting): a moved chair is a valid 4D observation and must not drag the pose. The principled composition: **scaffold-first, content only where scaffold underconstrains** — the `weakAxisFrac`/whitening machinery already names the weak eigen-direction, so content weight can be conditioned to contribute mainly along it. That's precisely the mode-2 payoff: one wall + floor constrain cross-wall + yaw + ty and leave the along-wall axis floating — the lumpy content is exactly what can pin that remaining axis.
>
> **Interactions to design when this gets picked up:**
> - **Classification source:** user-selected at location creation (the slider) vs. auto-detected (the data already exists — RoomPlan wall count/area, `weakAxisFrac`, classifier wall-face fraction) vs. hybrid (auto-suggest, user confirms). The observability math could *demote* a scan's mode automatically when the geometry doesn't support the selected one.
> - **Postprocess state machine (DECISION 3):** "no room achievable = bad scan" is only true in mode 1 — in modes 2/3 a missing RoomPlan room is *expected*, so the per-artifact prerequisites become mode-dependent (mode 2: plane-anchor sidecar replaces `CapturedRoomData`; mode 3: mesh is the only prerequisite).
> - **Ghost proxy:** mode 2 builds quads from persisted plane anchors instead of RoomPlan; mode 3 typically has no quads → decimated-full-mesh ghost (the decimation still-open item gains urgency there) — but per the decoupling above, any plane that *is* detected still becomes a quad in any mode.
> - **Per-mode gates:** mode 2 inherits Gate as-is (or the hybrid's composite gate); mode 3 revives `BakeGate`-style trust (converged + corr count + `horizMin` + finalRMS) applied at postprocess. A hybrid fit needs the gate to report *which terms* constrained which DOF (planes vs. content) — a pose pinned along the weak axis only by movable content is lower-trust on that axis by construction.
> - **Mode is per-location, not per-scan** — all generations of a location must register with the same method against the same canonical artifact, or cross-generation ε becomes method-dependent.

### Phase 4 — 3D stitch durability (pose graph over location frames) — *largest, server-involved*
Depends on Phase 1 (canonical frames must exist).
- [ ] **4.1** Define stitch links between **location canonical frames**, not scan instances (extend `PendingStitchLink` / `StitchLinkStore`).
- [ ] **4.2** Multi-constraint boundaries: several pin pairs (or overlap-ICP) per link, not one.
- [ ] **4.3** Server pose-graph optimization treating each link as a noisy measurement; 4D updates never touch the graph.
- [ ] **4.4** Versioned re-baselining op — **timeline-preserving**, **data-triggerable**, and **never moves the original baseline** (connector/stitch transforms are pinned to it). Fires manually or when Phase 2.2 reports a *clean* scan below the inlier-fraction floor / sustained structural-class change (regime 3).

  **Data model — canonical generations.** A location's canonical frame is an ordered list of generations, not a single map:
  - **Gen 0 = the original baseline, authoritative forever.** Connector transforms and stitch edges are stored in **gen-0 coordinates** and never move — so a re-baseline can't break the 3D graph or invalidate history.
  - Each later generation stores `transformFromBaseline` (gen 0's is identity), its bootstrap world map, and its scaffold mesh + registration quality (inlier RMS/fraction, # connector fiducials).
  - A 4D scan stores `(generationId, transformIntoGeneration)`; its position in the baseline = `gen.transformFromBaseline · transformIntoGeneration`. Everything resolves back to gen 0.

  **Solving `transformFromBaseline` (the old→new transform) — connectors are the bridge.** Use whatever of these survive, as a least-squares rigid fit:
  - **Surviving structural overlap** — ICP the new scaffold against the persisting subset of the baseline scaffold (floor, shell, unchanged walls). Same inlier-ICP, small-but-sufficient inlier set.
  - **Re-observed connector pins** — a connector is a *physical* point (a doorway); it almost always survives the change. Re-observe it and use connector positions as high-weight point correspondences. The thing we must preserve is also what measures the transform.
  - **Deliberate bridging scan** — a walk-through seeing both surviving-old and new geometry, captured when knowingly re-baselining.

  **Folds into the pose graph (4.3).** A generation is a **node**, `transformFromBaseline` is an **edge** with covariance from registration quality; connectors stay edges to neighbor locations in baseline coords. No separate machinery — the optimizer absorbs the noise.

  **Keep distinct from connector re-survey.** Frame re-baseline assumes connectors are *physically stable* (default). If a structural change actually *relocated* a link (doorway bricked up, new opening cut), that's a deliberate **re-survey of that one stitch edge** in baseline coords — a different op. Degenerate extreme: no surviving overlap *and* connectors gone = effectively a new location (re-survey connectors from scratch); flag it as the boundary where "re-baseline" stops being meaningful.
